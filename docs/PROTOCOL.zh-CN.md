# 单字节 HID 报告兼容方案

**简体中文** · [English](PROTOCOL.md) · [返回 README](../README.md)

已测试的 Google Chromecast Voice Remote：VID `0x18D1`、PID `0x9450`，
蓝牙型号标识 **ABBEY**，Firmware / Software **22.2 / 22.2**。
它在 Report 1 中声明两个 Consumer 数组槽位，但单按和松开时发送单字节载荷。
macOS IOHID / CoreHID 能收到双键报告，却丢弃这些不足长度的报告。
HCI 捕获中存在完整的按下和松开事件，说明丢失位于蓝牙接收之后、普通 HID 投递之前。
这也解释了更换电池或修改映射为什么没有解决单按漏键。

辅助服务通过私有 FIFO 读取 Apple PacketLogger 的实时流，利用配置中的遥控器地址，
从设备元数据和 LE 连接事件中识别连接句柄，再重组 ACL / L2CAP 分片。
只有指定 ATT 报告句柄（已验证为 `0x0046`）的通知或指示，以及含一到两个有效按键字节的报告会被转发。

另一只报告厂商 `zhuhai_jieli`、型号 `hid_mouse`、固件 0.0.1 的遥控器使用
`0x002b`，发送两字节小端 Consumer Usage。配置 `report_format: "consumer16"`
后，辅助服务将已核对的 14 个按键和松键通知转换为原有编号；未知用法、错误长度和
非配置设备/句柄仍被拒绝。`indexed` 为兼容旧配置的默认格式，不自动猜测载荷类型。

这款固件还会延迟语音松键通知：即使短按且没有音频，AUDIO_START 到 AUDIO_STOP
也约有 1.3 秒。应用读取设备信息中的厂商（0x2A29）、型号（0x2A24）和固件（0x2A26），
由 `RemoteCompatibilityProfile` 判断。三者全部匹配 `zhuhai_jieli` / `hid_mouse` / `0.0.1`
时才启用补偿：累计收到 550 毫秒解码音频后才判为长按，
静音样本同样计时，避免把松键通知的延迟误算为按住时长。
短按松开后重新开麦持续收音；再次按下时，即使固件复用当前语音流编号，也能停止。

其他厂商、型号、固件版本以及设备信息缺失的情况，继续使用原来的按下时长判断。
匹配时忽略大小写及字符串首尾填充，但不做前缀匹配，也不依赖蓝牙显示名称。
连接设备时会清空旧身份信息。语音补偿独立于按键协议选择。
遥控器设置通过 IOKit 读取已连接 HID 设备的 `DeviceAddress`、`PhysicalDeviceUniqueID`、
厂商、型号、固件及 VID/PID。物理 UUID 用于选中对应的 CoreBluetooth 语音设备，不会选取第一个同名设备。
已验证的 VID/PID 加 ABBEY / 22.2 匹配 `0x46` / `indexed`；完整 Jieli 身份加 VID/PID
匹配 `0x2b` / `consumer16`。未知身份只允许使用已经核对的手动参数。

辅助服务协议 v2 只接受配置用户 UID 发来的一条限长设备选择 JSON，严格验证字段白名单、
地址、格式、句柄、可选语音 UUID 和自动识别标志，不允许修改 UID/GID、socket 或可执行文件路径。
配置保持 root 所有并原子替换；应用回读验证后重连按键和语音，重新开始捕获以取得新的连接元数据。
非法请求和写入失败保留原文件。应用会先识别旧版辅助服务，不向其发送更新请求。

语音停止通知不能触发重复的关麦命令：遥控器主动松键时只结束本地手势，
停止确认只复位本地状态，避免在每次 MIC_CLOSE 都会产生 AUDIO_STOP 的固件上形成循环。

服务通过权限为 0600 的 Unix socket 仅向选定用户发送过滤后的按键数据，并校验连接方 UID。
应用校验服务端为 root，拒绝过期事件；断开连接和超时保护会释放按住的键。
因此 PacketLogger 是运行时依赖，不只是调试日志工具；不需要用户打开它的图形窗口。
辅助服务不会保存原始抓包文件，但兼容描述文件可能令 macOS 自身保存蓝牙原始日志。

麦克风使用独立的公开 ATVV BLE 服务，经标准 IMA ADPCM 解码后送往 BlackHole。
语音可用并不能证明按键投递正常。仓库不包含真实设备地址、原始录音或私人抓包，测试使用合成数据。
